# Агенты проекта

Разработка велась двумя ролями: кодер пишет, ревьюер проверяет. Контракт между ними — миграции в `supabase/migrations/`. Прогресс фиксируется в `CLAUDE.md`.

## Кодер (frontend)

**Зона:** всё вне `supabase/`. Если нужна правка схемы, он описывает её в отчёте и сам БД не меняет.

**Задача:** Vite + React + TypeScript, `@supabase/supabase-js`, `react-router-dom`, простой CSS, интерфейс на русском.

**Правила:**
- Вход по email и паролю, регистрации нет, роуты защищены.
- Экраны: список объектов `/`, карточка объекта `/objects/:id`, карточка задачи `/tasks/:id`, «Мои задачи» `/my-tasks` (только у исполнителя).
- Постановщик создаёт, редактирует и удаляет объекты и задачи. Исполнитель выбирается из `profiles` с `role = executor`.
- Статус меняется **только** через `supabase.rpc('change_task_status', ...)`. Прямой `update` поля `status` невозможен.
- Таблица переходов в одном месте: `src/lib/transitions.ts`. Кнопки показываются только допустимые для роли и статуса.
- Возврат на доработку заблокирован без комментария.
- Конфиг: `VITE_SUPABASE_URL` и `VITE_SUPABASE_ANON_KEY`, есть `.env.example`. `service_role` во фронтенде нет.
- Есть `vercel.json` с SPA-rewrite. `npm run build` проходит без ошибок.
- Делает только описанное: без лишних хелперов и рефакторинга.

**Отчёт:** файлы, как запускать, известные ограничения.

## Ревьюер (безопасность БД)

**Режим:** только чтение, файлы не правит.

**Что проверяет** (по каждому пункту вердикт ОК или ПРОБЛЕМА с `файл:строка` и фиксом):
1. Исполнитель не читает и не меняет чужие задачи, объекты и историю.
2. Прямой UPDATE `status`, `author_id`, `created_at` закрыт и не обходится через INSERT, RETURNING, политики или default privileges Supabase.
3. `change_task_status`:
   - разрешены ровно 6 переходов, остальные запрещены;
   - комментарий обязателен только для `in_review → rework`;
   - проверяется назначенный исполнитель;
   - нет утечки существования чужих задач;
   - `search_path` и `security definer` безопасны;
   - `EXECUTE` закрыт для `public` и `anon`;
   - есть блокировка `for update`.
4. `task_history` нельзя подделать, изменить или удалить через API.
5. Нет рекурсии RLS и лишней утечки через `profiles`.
6. `seed.sql` корректно создаёт пользователей в `auth.users` и `auth.identities`, идемпотентен.
7. Миграция применится на Postgres 15.

**Отчёт:** список «ПРОБЛЕМА: файл:строка — суть — фикс», затем «ОК».

## Порядок работы
1. Схема и RLS пишутся первыми, это источник правды.
2. Кодер и ревьюер работают параллельно.
3. Замечания ревьюера вносятся в миграции, затем проверяется фронтенд.
